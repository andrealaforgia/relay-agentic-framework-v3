**S3-5.1 · BLOCKING · A committed grant can strand work before its first effect.** Claim `integration.requested`, commit the grant, then kill the consumer before it creates the successor batch. Empty Redis and restart. The parent is `interrupted`, there is no `running` successor to recover, and re-announcement excludes commands with grants. The same gap exists when a review claim succeeds and pause intervenes before `prepare_review` issues its receipt. For the scripted integration handler, create the grant and successor batch in one transaction, or recover granted commands by inspecting their downstream records. For reviews, name the checkout receipt as the start boundary and recheck closure when issuing it, after the Git export. Test both gaps. Paid-call recovery can stay in 3b. **S3-5.2 · BLOCKING · An obsolete Builder command can become “still wanted” again.** Red R issues a build command. Green moves the behaviour to review. A Sentinel blocker returns it to `implementing` with the same R and issues a remediation command. The original build command now passes both checks in the proposed table. Its payload lacks the finding and names the original base. Give each Builder assignment a durable identity that is retired when that assignment finishes or is replaced. Deliver the original command after remediation is requested and assert that only the remediation assignment can start work. **S3-5.3 · BLOCKING · Resume can miss work for which there is no outbox row.** A green accepted during pause creates a pending review cycle and tasks. By the existing publication contract, review commands and capabilities are created only *after* the candidate ref is published. Publication is refused while paused, so scanning held or deliverable commands on resume finds nothing for this cycle. There is a second case: the last authorised integration settles during pause, with the list already sealed and assessed. Once its gate opening is suppressed, no later behaviour event is owed. Resume must schedule pending publication and re-evaluate ready story gates, as well as re-announcing commands and reconsidering story release. Test both cases with no new user action after resume. **S3-5.4 · BLOCKING · A retry from an older logical request can supersede newer checks on the same cycle.** Hold batch A during pause. On resume, delay its integration command and start an independent request B on the same satisfied cycle. A still has no successor, so its delayed command passes both proposed checks. Starting A’s successor can now supersede B, including a failing B whose results are about to settle. Preserve the slice 2b rule that only the current batch for the cycle may decide. Under the behaviour lock, require the named parent to remain the cycle’s current batch and replace it atomically. Test that B remains current and its failure sends the candidate back exactly once. **S3-5.5 · BLOCKING · “No command is delivered” needs a defined dispatch boundary.** A Redis publisher can select a deliverable row before pause and append it afterwards. A worker can also receive an entry that was already in Redis when pause committed. The claim guard can prevent either delivery from starting work. Define the guarantee as **no new grant after closure commits**, and require dispatch selected after closure to skip held commands. If physical publication after closure must also be prevented, include the outbox publisher explicitly in the locking protocol, acquiring the project gate lock before the outbox row. Test by holding publication between selection and Redis append.
