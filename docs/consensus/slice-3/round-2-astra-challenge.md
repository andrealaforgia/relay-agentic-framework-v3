All three matter in the two-story scripted slice. None requires bringing workers, real authentication or provider calls forward.

### Required before 3a-i

**S3-2.1 · BLOCKING · “Current story” gives the wrong answer on both sides of the approval gate.** `awaiting_approval` deliberately occupies the project slot. With no blocker or pause, `eligible(subject)` therefore returns true for that story, even for a Verifier proposing another behaviour. Conversely, the first `planned` story cannot satisfy “already current” to become released. V2 replaces v1 for 3a, so retain v1’s predecessor and approved-roadmap rules explicitly. Define eligibility **for the requested transition**: release selects a planned story from the approved roadmap when its predecessors are satisfied and the project slot is free; behaviour work requires a working story revision and the appropriate behaviour state and ordering; human approval requires the exact open gate. Serialize approval and selection of the successor, including across features. Test an attempted append while awaiting approval, behaviour 2 starting before behaviour 1 integrates, and two approved features competing for a slot that subsequently becomes free. The losing feature must eventually be reconsidered without a restart. [Project slot and eligibility](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-2-claude-design-v2.md:15) · [Original ordering rules](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-1-claude-design.md:23)

**S3-2.2 · BLOCKING · A gate must become stale when its basis changes.** V2 supersedes G1 when G2 opens. Suppose G1 is displayed, a permitted revision makes its sealed list obsolete, and the new list is still awaiting assessment. G2 cannot open yet. An `approve(G1)` can therefore release the next story on obsolete evidence. Either refuse that mutation while G1 is open or atomically supersede G1 and its inbox item when accepting the mutation. Under the same lock, a first human action must verify the current basis. Persist the manifest or an immutable reference to it, including the approved roadmap, story, ordered list, integrated evidence and exact assessment shown. A digest alone cannot reconstruct the review. Test approval **during the interval before G2 exists**, then restart and retrieve the original review unchanged. An identical retry of an action already committed should still return its receipt. [Gate and action rules](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-2-claude-design-v2.md:42) · [List revision and assessment](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-2-claude-design-v2.md:52)

**S3-2.3 · BLOCKING · A reused request ID can acknowledge an action the PO never performed.** V2 says the same request ID returns the first receipt. If a client accidentally reuses the ID from `approve(G1)` for `request_changes(G2, reason)`, the second call can appear successful while G2 remains untouched. Scope the key to the authenticated principal and bind it to the target, action and canonical payload. An exact replay returns the original receipt; different content returns a conflict with no effect. Commit the receipt, gate outcome, inbox change and resulting release together. Test both a lost reply and conflicting reuse across two gates. 3a-i needs the `request_changes` **disposition** for its race test; the corrective workflow can wait. [Human-action contract and planned tests](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-2-claude-design-v2.md:44)

### Points that can wait

**S3-2.4 · BLOCKING for 3a-ii only · Reassessment needs a durable action to resume and a current revision to authorise.** A paused integration batch is closed as `held`, but reassessment is defined over held **commands**. If the batch produced no command, resume can leave the behaviour stranded. Conversely, the same story can remain current after its red execution or decision revision changes, so releasing every held command for that story can revive obsolete work. Reassess the pinned task inputs and current gate basis. Discard superseded commands, create exactly one fresh integration attempt when required, and make cancelled work terminal. Also invalidate or suspend a story gate when a blocker affects evidence in its manifest, even if the question names only one behaviour. Test pause during the last check, restart, then resume both with unchanged inputs and with one input superseded. [Held batch and reassessment](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-2-claude-design-v2.md:26) · [Existing batch replay](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:793)

**S3-2.5 · BLOCKING for 3a-ii only · A story-wide exemption can break the old obligation before its replacement reaches trunk.** Suppose corrective story C has two behaviours and only C2 replaces A with B. Under v2, C1’s candidate also omits A. It can integrate while satisfying neither A nor B. Bind the PO’s authority to the exact old obligation and replacing behaviour revision. C1 must still pass A. C2 may omit A only while demonstrating B, and retirement becomes global on verified integration of C2. Specify how the same authority is obtained when `request_changes` revises the original story without opening a corrective roadmap gate. Keep ordinary successors behind the correction until it is accepted. [Correction and supersession rules](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-2-claude-design-v2.md:61) · [Current regression selection](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:875)

I would keep the **3a-i exit test** narrow: start with an approved two-story roadmap, integrate story 1, prove that its displayed gate prevents further implementation, restart with Redis empty, retrieve the same review, and approve it exactly once to release story 2. Questions, pause/cancel barriers, correction and feature completion belong in 3a-ii. Paid-call recovery and worker isolation belong in 3b. Trusted live confirmation belongs in 3c.
