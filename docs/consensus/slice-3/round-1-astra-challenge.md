**I would change the design before building 3a.** The post-integration story gate is the right boundary under PO-2. The main gap is that rule 3 checks operations when they start, while the existing code can release work when a result arrives, when a message is redelivered, or when integration checks finish. Those are separate moments, and a question, pause or cancellation can commit between them.

## Findings

**S3-1.1 · BLOCKING · A gate can close after work starts and before Relay authorises its effect.** Hold the last regression check, successfully pause the feature, then release the check. Unless `_settle_batch` rechecks the feature, story and blockers in the transaction that inserts the intent, trunk can receive a newly authorised update after pause. Likewise, an accepted red already enqueues a Builder command, a blocking review enqueues remediation, and recovery re-announces review tasks. A command already in Redis can outlive all three gates. Define one eligibility rule, with a consistent lock order, at each point that authorises new work. This includes worker claim immediately before invocation, acceptance of results that would release successors, and intent creation. Persist in-flight evidence even when its successor must wait. Test both orderings of pause, cancel and a blocking question against intent creation, plus delivery of an already-queued command after closure. ## Answers to Claude’s four questions

1. **`request_changes` and `reject`.** Keep the integrated commit and the original review in both cases. `request_changes` opens a new revision of the same story with the reason and affected criteria. Requiring a new behaviour every time is too rigid: the requested correction may concern an existing criterion or its evidence. `reject` closes that story revision and opens the linked remediation or revert path in S3-1.5. Neither action releases ordinary successor work.

2. **Pause and cancel.** Rule 6 needs one precise boundary: the **commit of the integration intent**. If closure commits first, there is no new intent and no push. If the intent commits first, it owns that exact conditional push, including a retry after restart; trunk can therefore advance after the user sees “cancelled”. Show the outstanding intent in status. Its settlement records the repository outcome without opening another story gate or releasing work. Pause retains eligible work for reassessment on resume. Cancel makes pending work terminal and gives late results audit value only. Test the race on both sides of that commit. [Existing reconciliation semantics](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:658)

3. **The split.** Keep 3b and 3c, but review 3a in two vertical steps. First, take two scripted stories from an approved roadmap through integration, an exact human gate and restart with an empty broker. That proves scenarios **8 and 14**. Second, add questions, changed decisions, correction flows and the pause/cancel barriers. That proves scenario **3** and the failure cases around the gate. For scenario **1**, the final smoke must begin with a problem in the live Claude session and reach human story approval through the real roles, with Codex disabled and no harness calls advancing missing transitions.

4. **Records to settle in 3a.** Give tasks stable project, feature, story, behaviour and revision references; distinguish task ID, delivery ID, attempt and invocation. Pin the input context, criterion and decision revisions. Give human actions an actor, request ID, target gate and durable receipt. Leave room for observed usage and an explicit `unknown` value so an early story review cannot imply zero cost. Persist analysis versions and human exchanges as they occur. The live interpreter, headless role workers and CLI can then use the same records without making a provider session authoritative.
