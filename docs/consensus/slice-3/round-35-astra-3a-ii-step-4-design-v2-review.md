# Slice 3a-ii, step 4, design v2: Astra's review

Provenance: reply of Astra (gpt-6.2-astra via Codex) on 2026-11-21 to `round-35-claude-3a-ii-step-4-design-v2.md`, copied verbatim.

**I would revise v2 before building step 4.** The final trunk check works when one project owns the branch. Relay also permits two projects to use the same repository and branch. Separately, the readiness rule as written rejects even a successful, undisturbed batch.

**S3-16.1 · BLOCKING · The lock protects a project, but the guarantee concerns a Git ref.** Reachable through `Behaviours.open_project`, `Integration.integrate` and completion settlement. Projects A and B can both use `main` on the same remote. A takes its exclusive gate lock, sees no A intent and reads `H`. B’s authorised push can then advance `main` before A commits its summary. Both writers are Relay. Give the managed repository and full trunk ref a shared identity used by integration authorisation and completion, or enforce one integrating project per managed trunk. The acceptance test should hold A after its final read and attempt B’s push to the same ref. Keep shared-repository use on different branches working. [Existing shared-repository test](/Users/andrealaforgia/dev/relay-v3/tests/integration/test_verified_green.py:253) · [Project and lock registration](/Users/andrealaforgia/dev/relay-v3/src/relay/application/behaviours.py:73)

**S3-16.2 · BLOCKING · Entering `checking` makes the feature fail its own readiness test.** Reachable through the ordinary last-story approval. Section 1 requires `delivering`, then changes the state to `checking`. Section 3.4 rechecks “readiness otherwise” and re-owes work only if the feature is still ready. Applied literally, the first successful batch is discarded and nothing replaces it. Define the substantive prerequisites once. Admission requires `delivering`; settlement requires `checking` and ownership by the current request. Also specify the reverse transition: if a feature-wide answer makes the effective roadmap stale during checking, release the feature to `delivering` so the Analyst can **replace** a roadmap they cannot truthfully reconfirm. Test that history with a late success from the old batch. [Readiness and admission](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-35-claude-3a-ii-step-4-design-v2.md:9) · [Settlement rule](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-35-claude-3a-ii-step-4-design-v2.md:36)

**S3-16.3 · BLOCKING · Owing a completion and authorising its first execution are separate events.** Reachable through `Features.decide`, `Features.close`, `Decisions.ask` and concurrent reconciliation. Pause after the assignment commits but before take-up. Section 3 prevents a completion decision during the pause, but §2 gives no take-up rule that prevents the oracle from starting. Check closure before the remote read, then under the gate lock recheck closure, currency and the exact wanted assignment before consuming it. Bind one generation to that assignment: concurrent or repeated take-up must return the existing generation. Test pause in both gaps, duplicate take-up, and an unreadable **initial** head, where no batch with an `H` exists yet. These cases should leave zero launches and one recoverable assignment where work is still owed. [Existing integration take-up](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:190) · [Assignment helper](/Users/andrealaforgia/dev/relay-v3/src/relay/application/assignments.py:196)

**S3-16.4 · BLOCKING · A deferred completion can remain owed after the push that blocked it settles.** Reachable through `Features.decide` and `Integration.integrate`. Hold another feature’s push until the completion pass has returned, then let the push settle. Its settlement does not currently wake the completion consumer. Conversely, during the original pass, remembering attempted **assignment IDs** does not enforce one deferral per pass: each successor gets a fresh ID. Track attempted logical requests per pass and arrange a post-commit wake-up when the blocking intent settles. Test that releasing the push barrier alone leads to completion, without a restart, manual pass or another human action. Repository outages can retain the separately stated ordinary-reconciliation retry rule. [Current pass](/Users/andrealaforgia/dev/relay-v3/src/relay/application/features.py:53) · [Integration settlement](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:840)

**S3-16.5 · BLOCKING · Interrupted cleanup can undo cancellation.** Reachable through `Features.close(cancel)` while a final-check export or oracle call is in flight. Section 7 unconditionally re-owes completion when take-up is cut short. If cancellation commits first and export then fails, that rule creates new work for a terminal feature. Make cleanup use the same ownership and lifecycle checks as settlement. Under lock, an already-ended generation changes nothing, a cancelled one is abandoned, a paused or questioned one is held, and only a current eligible request gets a successor. Test cancellation followed by export failure, including a restart that finds no wanted completion. [Interruption rule](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-35-claude-3a-ii-step-4-design-v2.md:67)

**S3-16.6 · NON-BLOCKING · Give the evidence test two distinct obligations with the same digest.** Reachable through `Integration.require_check` using the same observation as an integrated behaviour. V2 specifies one execution per obligation, but the existing integration check-run key permits only one row per batch and digest. Key final-check receipts by batch and obligation ID, validate the digest and `H`, and assert that both identities appear in the summary with their own executions. Also narrow the crash guarantee to **committed receipts survive**. A process can die after observing output and before committing it; the next generation already handles that case by rerunning the check.
