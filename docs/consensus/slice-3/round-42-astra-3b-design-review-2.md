# Astra's second review of the slice 3b design (v2)

Provenance: written by Astra (gpt-6.2-astra via Codex) on 2026-11-21 in reply to `round-42-claude-3b-design-v2.md`; copied verbatim below.

**Step 1 still needs changes before build.** V2 closes the duplicate paid call between Record and Apply. Its remaining problem is deciding when the *same assignment* legitimately needs another invocation. As written, the Verifier can ask a question, the Product Owner can answer it, and admission will refuse the resumed work forever.

I checked the design against the application at `fa83d49` and the installed Claude Code 2.1.330 help. No paid call was made. Each finding below is reachable through a proposed worker entry point and an ordinary Relay operation or recovery path.

**S3-19.1 · BLOCKING · Step 1, exercised in step 3 · Reachable through `ask`, `answer` and redelivery.** Section 3 marks the question invocation `applied` and leaves the assignment `wanted`. After the answer, a worker claims it, but section 1.2 reads the latest invocation **of the assignment** and stops at `applied`. Sending back a submitted roadmap has the same problem. Give each occasion on which work becomes owed a durable identity. Redelivery within that identity finds its existing result. Answering a question or sending back a proposal creates one successor when work is still owed. Changing the comparison to grant alone would allow routine grant revocation to authorise fresh spend. Test the old delivery arriving alongside the successor and require exactly one new call. [Admission and question rules](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-42-claude-3b-design-v2.md:29)

**S3-19.2 · BLOCKING · Step 1 · Reachable through the Product Owner’s `retry` and a late provider result.** Admission refuses `parked` before it examines `retries_allowed`. Adding one to the counter therefore cannot wake the work as specified. A general counter also leaves a race if the original result arrives after permission was given but before it was consumed. Make `retry` a receipted human action targeting the exact uncertain invocation. In one transaction it clears that park, authorises one successor and arranges delivery. Serialise admission with late-result recording. If the result wins, apply it and retire the unused permission. If the successor wins, keep the old result and its usage as evidence. Replaying the human action must never buy another attempt. [Admission and late-result rules](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-42-claude-3b-design-v2.md:36)

**S3-19.3 · BLOCKING · Step 1 · Reachable through `Assignments.claim` followed by worker exit.** Kill a worker after claim commits and before Intend. There is no invocation for the ordinary recovery scan to find. The replacement worker has a different identity and cannot claim the granted assignment. Only a control-plane restart is specified to recover that grant. Record the worker process identity on the grant at claim and have the ordinary recovery pass inspect dead owners’ grants, including those with zero invocations. That history should return the assignment to `wanted` without opening a paid-call inbox item. Keep the separate rule for a dead owner with a durable result. [Claim ownership](/Users/andrealaforgia/dev/relay-v3/src/relay/application/assignments.py:386)

**S3-19.4 · BLOCKING · Step 1 effect contract, exercised in step 2 · Reachable through two deliveries of a `returned` build.** Both deliveries can be handed the same invocation to apply. If both observe `green` unfinished, both can enter `run_green` before either records the outcome. Today each call creates a fresh run ID. There is also a gap where cancellation can commit after `retained` and before `published`, leaving the supervisor to push an attempt for retired work. Give each effect a stable identity and one transactional admission under its applicable grant and closure rules. Bind the oracle run and its verdict to that identity, and define recovery when a run was started but no verdict committed. Test concurrent Apply at `green` and cancellation between retention and publication. [Green run creation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/assignments.py:145) · [Build effects](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-42-claude-3b-design-v2.md:69)

**S3-19.5 · BLOCKING · Step 1 record contract, implemented in step 2 · Reachable through Builder recovery immediately after Record.** The Builder now returns its implementation through the workspace. The terminal envelope can commit as `returned` before Apply pins the tree. If the workspace disappears with the worker, recovery has the note and no implementation. Define what makes the workspace recoverable at Record, or retain an immutable tree before marking the build ready to apply. Keep the terminal event and usage even if retention fails. The decisive test stops the worker immediately after `returned`, removes its scratch directory, and recovers the exact candidate without invoking Claude again. [Retention order](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-42-claude-3b-design-v2.md:71)

**S3-19.6 · BLOCKING · Step 2 · Reachable on the first remediation.** Both review and integration send the Builder the **candidate being repaired** as `base_revision`. Section 4 always exports the red revision. On a remediation, the files that prompted the finding can therefore be absent from the workspace. Export the assignment’s recorded base, preserve the accepted red as the ancestry requirement, and allocate the Git attempt number per project and behaviour across build and remediation assignments. Test a finding about a file added by the first build. The repair must start with that file present and leave the first attempt ref intact. [Review remediation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/reviews.py:735) · [Integration remediation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:709) · [Attempt ref identity](/Users/andrealaforgia/dev/relay-v3/src/relay/git/checkout.py:124)

**S3-19.7 · BLOCKING · Step 2, before tool-enabled calls · Reachable through the Builder launch.** A pass keyed only to CLI version can survive a change to managed settings, role policy or host sandbox configuration. The proposed suite also accepts the model’s account of what happened. A model can report that a read was refused without issuing the tool call. Bind the pass to the effective configuration and runtime being authorised. Require independently observed tool attempts and outcomes, including a permitted operation that succeeds. Check child-process credentials with a harmless test value, and check candidate-local `CLAUDE.md` as well as settings and agents. Anthropic documents separate controls for credentials inherited by sandboxed commands. **D-5 can remain deferred once this boundary is demonstrated.** The version-only pass does not establish it. [Confinement proposal](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-42-claude-3b-design-v2.md:139) · [Claude sandbox credential controls](https://code.claude.com/docs/en/sandboxing#protect-credentials)

**S3-19.8 · BLOCKING · Step 3 · Reachable through a newly satisfied review and `require_check`.** I accept owing the first integration in the review transaction. That changes who owns generation one. Today, if a required check is added during the first batch, `_discard` ends it because its caller can ask again. An interrupted first batch has the same rule. Under 3b that caller is the control plane, and the review gate will not become satisfied a second time. Give the first assignment a cycle-bound take-up path and keep the integration owed after an interrupted or discarded first batch while the cycle remains eligible. Test adding a check during generation one, then reaching trunk with no manual integration request. Preserve the human retry boundary for a remote refusal. [First-generation discard](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:1130) · [Interrupted first batch](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:502)

**S3-19.9 · BLOCKING · Step 3 · Reachable through contract amendment and a decision at an open story gate.** Two existing transitions still lack a worker to carry them forward. `amend_contract` returns the existing behaviour to awaiting red, but the only red in the task table follows a *new* proposal. Separately, a decision can clear a story’s seal and supersede its gate. Once all owners reconfirm, there may be no new release, integration or `request_changes` to trigger another `specify` or `seal`. Derive the work owed in both states and recover it after restart. Test a fresh red against the amended behaviour’s existing identity, and a fresh seal and assessment after reconfirmation with every behaviour already integrated. [Amendment](/Users/andrealaforgia/dev/relay-v3/src/relay/application/decisions.py:570) · [Seal invalidation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/decisions.py:779)

Of the previous findings, **S3-18.3, S3-18.5 and S3-18.10 are answered**. I also accept the revised decisions to keep transcripts out of recovery, store the reviewer’s checkout receipt, disallow assumption-only replies, and owe the first integration durably. S3-19.1 to S3-19.5 need resolution before step 1. The remaining findings can wait for their stated build steps.
