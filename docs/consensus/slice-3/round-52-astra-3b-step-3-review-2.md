**Step 3 still has reachable cases where an old worker changes current work, or where the next step requires a person to do the worker’s part.** The most serious is proposal withdrawal. A reply written before a second Product Owner decision can withdraw the proposal under that second decision and retire the reconfirmation owed to its author.

**3B-S3-2.1 · Blocking · Reachable through `ReconfirmTask` and a second feature-wide decision.** Let the Analyst’s `to_be_replaced` effect start, then commit another feature-wide decision before `give_up_proposal` takes the gate. The proposal still has the same revision number, but the first grant and decision basis have been superseded. Withdrawal checks only the proposal number. It closes the proposal and retires the *new* reconfirmation. Even without a race, withdrawal retires its own assignment in `perform`, so `_mark` records the successful invocation as `overtaken`. Put withdrawal and its invocation mark in the same transaction under the current grant, basis and effect try. Test both the stale reply leaving the newer reconfirmation intact and an ordinary withdrawal ending `applied`. **3B-S3-2.2 · Blocking · Reachable through QA and Sentinel on the same candidate.** QA starts marking a question and holds the shared project gate and the behaviour row. **3B-S3-2.3 · High · Reachable through a running red, `pause` and `resume`.** The pass grants the red but leaves `first_effect_at` empty while the oracle runs. A pause takes back that apparently unused grant. Resume can launch the same red again while the first oracle is still running. The first caller’s cleanup also matches only the assignment ID and `granted` state, so it can release the second caller’s grant. Bind launch, verdict and cleanup to the assignment, cycle and grant that took the red. Hold the oracle across pause and resume and count executions before releasing it. The same admission rule should cover a direct `run_red`, which currently also bypasses the wait for a proposed supersession.
