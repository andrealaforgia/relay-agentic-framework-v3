**3B-S1-3.1 · Blocking · Reachable through `Invocations.apply` and `recover`.** An effect that advances the story’s list revision cannot reliably use the new `settle` API. Suppose the list is at N and the callback intends to advance it to N+1 inside `settle`. If `perform` reports N+1 in `stands`, `_mark` compares N+1 with the database *before* calling `settle` and declares the invocation overtaken. If it omits `stands`, the write succeeds but the next effect still expects N. The existing test avoids both outcomes by committing the revision change in `perform`. That exposes the removed guard: a concurrent pass can see N+1, mark the invocation `overtaken`, and then the original `_mark` can accept N+1 from `detail` and still call `settle`. Check the invocation state and **pre-effect** versions under the lock, then commit the workflow change, its resulting versions and the effect mark together. Test a revision-changing `settle` followed by a second effect, and run recovery during the existing version-changing example. [Settlement](/Users/andrealaforgia/dev/relay-v3/src/relay/application/invocations.py:519) · [Existing test](/Users/andrealaforgia/dev/relay-v3/tests/integration/test_invocations.py:868)

**3B-S1-3.2 · Blocking · Reachable through `Invocations.apply` and the ordinary recovery pass.** Cancel an Apply after it takes an effect, keeping its worker session alive. The `finally` clears the local token, but the durable effect still says `started` by that worker. The new test retries using the **same** `WorkerSession`, which can see that its token is gone. `Features.reconcile` uses a different session and checks only whether the original process is alive. Every pass therefore returns `busy` for an effect nobody is performing. Relinquish the durable ownership for that specific try when Apply is cut short. The regression should end with an ordinary pass, the original worker alive, one application and no new provider call. **3B-S1-3.4 · High · Reachable through `Behaviours.reopen_red` and a late effect refusal.** Let the third paid attempt return a usable reply and start `perform`. Reopen the red, retiring the build, then let `perform` raise `ActionRefused`. This path goes straight to `_reject`, bypassing `_mark`’s check for ended work. The invocation is still `returned` and the try is still current, so `_reject` records a defective reply and `_park` opens a **new** inbox item on the retired assignment. A subsequent `retry` is acknowledged as effective. Recheck the work’s disposition in the transaction that records the refusal, including after a `settle` refusal has rolled back. This history should end `overtaken`, with no park or inbox item. **3B-S1-3.5 · High · Reachable through roadmap approval and `Invocations.decide`.** Park an Analyst’s `correct` invocation, then approve a roadmap containing the correction through `Stories.decide`. Approval sets the assignment to `done` directly. It leaves `parked` and the inbox item intact, so the Product Owner can authorise a retry of a completed correction. There is a second consequence if the original result arrives after approval: `_ended_for_good` recognises `retired`, but skips the grant comparison for `done`, so a callback can still run on that finished assignment if the basis is unchanged. Close parked work on independent completion as well as retirement, and distinguish completion by this effect from completion by another action. Test both a late human retry and a late provider result. **3B-S1-3.6 · High · Reachable through `Invocations.recover` racing `record`.** A rejected story in F1 can owe the Analyst a correction while F2 has a granted build in the same project. Recovery parks the dead Analyst’s call and appends an event, locking the project row. It then asks for **all** granted assignment rows before committing. Concurrently, the builder’s Record can hold its assignment row and need the project row to append its event. That is a project-to-assignment versus assignment-to-project deadlock. Process each recovery candidate in its own consistently ordered transaction and recheck eligibility there. The two-feature history avoids any need to manufacture concurrent builds. [Recovery transaction](/Users/andrealaforgia/dev/relay-v3/src/relay/application/invocations.py:705) · [Granted-assignment scan](/Users/andrealaforgia/dev/relay-v3/src/relay/application/invocations.py:735) · [Ledger allocation](/Users/andrealaforgia/dev/relay-v3/src/relay/persistence/ledger.py:39)

**3B-S1-3.7 · High · Reachable through admission racing a liveness probe.** `is_alive` temporarily acquires the dead worker’s session-level lock to discover that it is free. During that interval a second observer can report the worker alive. Admission now uses that observation as permission to buy a call. For example, one worker can hold grants on two assignments. After its dedicated connection drops, recovery probing one assignment can make admission on the other accept the old worker. Cancellation between the probe’s lock and unlock can extend that interval across reuse of the pooled connection. Verify which backend owns the worker lock without temporarily impersonating its owner. The regression should require zero admissions during a concurrent probe of a dead worker.
