> Provenance: `gpt-6.2-astra`, reasoning effort high, same Codex session. Reviewed commit `a16f971`.

**I would hold slice 3a-i at `a16f971`.** The restart path meets the core requirement: PostgreSQL retains the open gate, its manifest and the human-action receipt after Redis is emptied. The main blockers are reachable through ordinary application calls. Integration can deadlock with assessment, a delayed assessment can certify the wrong list, and the roadmap shown to the human can differ from the roadmap Relay releases.

### Findings

**3A-1.1 · BLOCKING · Integration and assessment take the story and project locks in opposite orders.** `_converged` appends `behaviour.integrated`, which updates and locks the project row, then calls `evaluate_story_gate`, which locks the story. `assess` and `seal` lock the story first, then append a project event. If integration holds the project while assessment holds the story, PostgreSQL must abort one transaction. Git may already have advanced, leaving settlement to recovery. Acquire the story lock after the behaviour lock and before the first project-row write in `_converged`. Put a barrier between the two acquisitions and assert that both calls finish, with one integration record and one gate. [Integration settlement](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:701) · [Assessment](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:194) · [Implicit project lock](/Users/andrealaforgia/dev/relay-v3/src/relay/persistence/ledger.py:41)

**3A-1.2 · BLOCKING · Replaying an already-decided roadmap can deadlock release of its first story.** Take two approved features, with B waiting behind A. Approving A’s final story holds the project lock and then updates B’s feature row in `release_next`. A simultaneous exact replay of B’s roadmap approval locks B’s feature and waits for the project *before* consulting the receipt. This gives a deadlock even though the replay has nothing to change. A fresh stale request against B’s decided roadmap reaches the same lock sequence, so a fast path for exact replays alone is insufficient. Make cross-feature release and decision handling follow one compatible locking protocol. Test both calls concurrently and require the original receipt and exactly one release of B. [Decision locks](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:244) · [Successor feature update](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:425)

**3A-1.3 · BLOCKING · `seal` and `assess` bind the caller’s statement to whichever revision is current on arrival.** An Analyst reads sealed list L1. The Verifier appends B2 and seals L2. The Analyst’s delayed `assess(..., "B1 alone will do")` is accepted as the sole assessment of L2. The existing test covers an assessment *stored before* the append. It misses an assessment *delivered after* resealing. Require the expected story and list revisions on both operations, compare them under the story lock, and refuse a mismatch without recording a seal or assessment. [Seal](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:156) · [Assessment binding](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:200) · [Existing test ordering](/Users/andrealaforgia/dev/relay-v3/tests/integration/test_story_gate.py:393)

**3A-1.4 · BLOCKING · A road­map approval can release a story absent from the displayed manifest.** `publish_roadmap` iterates the caller-owned `Sequence` to insert stories, then iterates it again to assemble the manifest. There are database awaits between those reads. A caller can remove S1 from its list after S1 was inserted but before the manifest is assembled. The human sees the remaining stories, approves them, and `release_next` selects the undisplayed S1 from the database. `StoryDraft` being frozen also leaves its `criteria` mapping mutable. Snapshot the ordered drafts and criteria once before the first await, or build the manifest from the inserted rows. Test mutation across that boundary and compare the displayed order and criteria with the rows eligible for release. [Roadmap insertion](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:118) · [Manifest construction](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:132)

**3A-1.5 · BLOCKING · The human review omits how a finding was settled.** A high Sentinel finding verified fixed on the integrated candidate can still have stored status `open`. The proof of the fix lives in `finding_verifications` for that review cycle. `_story_review` selects only the finding’s ID, role, severity, status and claim. The human can therefore see an apparently unresolved high finding with no explanation of why integration proceeded. It also omits withdrawal reasons and the promised explicit contract digest. Assemble the manifest against the **integrated cycle**, including its verification or withdrawal record and contract digest. Test a blocker raised on A, verified fixed on B, and displayed after restart. [Manifest query](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:592) · [Verification and withdrawal records](/Users/andrealaforgia/dev/relay-v3/src/relay/application/reviews.py:558)

**3A-1.6 · BLOCKING · An open gate’s finding can change through the normal API without making the gate stale.** Open a story gate containing a low, open finding. `Reviews.dispute` still accepts a dispute and changes the finding to `disputed`. The first approval then succeeds because `_basis_now` checks only the story revision, sealed-list revision and assessment ID. The stored review still describes the earlier finding state. For 3a-i, refuse a disposition-changing dispute once its story is at the gate, serialising that check with gate opening. Alternatively, supersede the gate and inbox item atomically. Test `dispute` racing gate opening and a first approval after the dispute. [Dispute mutation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/reviews.py:503) · [Basis comparison](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:456)

**3A-1.7 · BLOCKING · Caller payload can overwrite the authoritative decision event.** `decide` writes `gate_id`, `by`, `request_id` and `manifest_digest`, then expands `action.payload` over them. An approval carrying a payload field named `manifest_digest` commits the correct state transition alongside a permanent ledger event naming a different review. Store user-supplied fields under a separate key or validate an action-specific payload schema. Freeze that payload once for validation, hashing, audit and receipt storage. Test that accepted payload fields cannot alter the recorded actor, target or digest. [Decision event](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:274)

**3A-1.8 · BLOCKING · Behaviour ordering has a production bypass that v2.1 did not authorise.** `open_project(..., behaviours_in_order=False)` lets B2 enter test design before B1 integrates. The specification’s default of one active *story* is a different rule from v2.1’s explicit predecessor requirement for *behaviours*. Keep the slice-2 concurrency coverage through a fixture that arranges the competing candidates, or negotiate a product policy change separately. Under the accepted design, the normal project API should preserve the ordering guarantee. [Project option](/Users/andrealaforgia/dev/relay-v3/src/relay/application/behaviours.py:64) · [Conditional guard](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:354) · [Accepted requirement](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-3-claude-design-v2.1.md:10)

**3A-1.9 · BLOCKING · A change request carries the old seal into the new story revision.** `_settle_story` increments `revision` but leaves `sealed_revision` equal to `list_revision`. Immediately after `request_changes`, the Analyst can call `assess` without any Verifier action. All the old behaviours are already integrated, so the new gate opens. The correction workflow can wait for 3a-ii. Invalidating the old seal belongs in the transaction that changes the revision. Test that assessment alone cannot reopen the gate. [Change-request transition](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:488) · [Seal check](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:196)

**3A-1.10 · NON-BLOCKING · Concurrent request-ID reuse across projects escapes as a database error.** The receipt key is global to `(principal, request_id)`, while `decide` serialises on one project. Two simultaneous requests by the same human against different projects can both observe no receipt. The losing insert rolls its transaction back, preserving gate safety, but returns a PostgreSQL uniqueness error instead of the specified conflict. Arbitrate on the receipt key and test the two-project race. [Receipt lookup](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:636) · [Receipt constraint](/Users/andrealaforgia/dev/relay-v3/src/relay/persistence/migrations/0007_stories.sql:117)
