# Slice 3c: Astra's first review of the design

Provenance: written by Astra (gpt-6.2-astra via Codex) on 2026-11-27 in reply to `round-57-claude-3c-design.md`; copied verbatim below. Round one of at most three for this design (D-8).

**I would change the contract before building step 1.** On the ordinary build path, the worker publishes the candidate and runs the green oracle *before* the callback that 3c proposes to replace with a wake. The process split therefore needs a durable hand-off earlier than the design specifies. The other step 1 blockers concern who owns recovery and which project a process is acting for.

All eleven findings below have a route through a proposed command or an existing application service. The later-step findings can wait for their named step.

| Finding | Step | Reachable through |
|---|---|---|
| 3C-1.1 | 1 | The first successful `build` or `remediate` reply |
| 3C-1.2 | 1 | `relay up` losing its lock connection during a run |
| 3C-1.3 | 1 | Two projects with work outstanding at the same time |
| 3C-1.4 | 1 | Initialising a second project against the same database |
| 3C-1.5 | 1–2 | `init`, `passphrase`, or changing the file read by a worker |
| 3C-1.6 | 2 | Confirming a prepared integration retry after a second refusal |
| 3C-1.7 | 2 | Losing the reply to `feature start` or `confirm` |
| 3C-1.8 | 2 | A failed final check or a refused Git push |
| 3C-1.9 | 3 | `costs` on a call billed to two models |
| 3C-1.10 | 4 | Starting the Product Owner’s tool-enabled session |
| 3C-1.11 | 4 | Losing that session before the person confirms |

**3C-1.1. Hand the retained build to the control plane.** Today `BuildTask` pushes the attempt ref with the supervisor’s access and calls `run_green` during apply. A worker configured as §1 requires cannot finish that apply. Make the committed `returned` invocation and its retained commit sufficient for the control plane to take those effects. Wake it at that commit. Prove the split with a Builder process that has neither Docker access nor publication credentials. Stop it after `returned`, then require one published attempt and one effective green verdict without another provider call. [Build publication](/Users/andrealaforgia/dev/relay-v3/src/relay/application/tasks.py:696) · [Green observation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/tasks.py:753) · [Worker wake](/Users/andrealaforgia/dev/relay-v3/src/relay/application/worker.py:168)

**3C-1.2. Losing leadership must stop the former owner from starting more work.** Drop only the advisory-lock connection while the first control plane is waiting for Git or Docker. A second `relay up` can acquire the lock and run startup recovery while the first process still has live pooled connections. Specify how a process that loses leadership is fenced from authorising another effect, and how its already-authorised work settles through the existing intent or generation. Exercise this with the first process still alive. Killing the process in the proposed smoke misses the overlap. [Startup recovery](/Users/andrealaforgia/dev/relay-v3/src/relay/application/features.py:105)

**3C-1.3. A pass for B currently does work for A.** `Features.reconcile(project)` invokes an integration reconciliation and a candidate publisher that both scan *all* projects. Giving A and B one task each still lets both tasks handle A’s outstanding work. Scope those scans to the project, or give the global scans one owner. Test with A’s remote held and B otherwise ready. B should progress, and B’s wake should launch no operation against A. [Pass](/Users/andrealaforgia/dev/relay-v3/src/relay/application/features.py:148) · [Integration scan](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:374) · [Candidate scan](/Users/andrealaforgia/dev/relay-v3/src/relay/application/reviews.py:214)

**3C-1.4. Define which configuration governs B.** Start `relay up` and a worker in A, then initialise B against the same database with a different mirror root, agent path or per-call budget. Both processes now serve B. Discovery from their working directories still yields A’s file. Define which settings belong to the installation and how a process resolves the rest by project identity. Test B being added while the processes are running and again after restart. In particular, the process taking over a returned build must find the exact commit the worker retained.

**3C-1.5. Give the passphrase and the policy statement a trusted owner.** `policy state` requires confirmation, yet §2 makes the statement, its author and its date ordinary fields in a repository-discovered file. Editing that file can change what a worker accepts as the operator’s statement. Use a trusted installation record for the authenticated statement and its revision. Specify atomic first enrolment and require the existing passphrase for rotation. A second `init` or another project checkout must preserve the existing authority. This matters from step 1 because workers already use the statement to admit calls. [D-10](/Users/andrealaforgia/dev/relay-v3/docs/DECISIONS.md:31)

**3C-1.6. Bind confirmation to the particular refusal the person saw.** Prepare `retry-integration B1` after refusal I1. Someone retries directly, and the repository refuses I2 within the hour. Today the service looks up the *latest* intent for B1. Confirming the old code would authorise a retry of I2. Freeze the project, subject, action, arguments and expected record identity at preparation. Compare them in the deciding transaction. Show the action and its actual reason or answer on the same trusted terminal that reads the passphrase. In this history the old code must return `stale`. The existing human-action digest covers the target, action and payload; it does not establish which refusal was displayed. [Retry lookup](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:407) · [Human-action digest](/Users/andrealaforgia/dev/relay-v3/src/relay/domain/story.py:253)

**3C-1.7. Make the lost-reply promise work for the first command.** `open_feature` has no request receipt today. If `feature start` commits and the terminal dies before printing its generated request ID, the person has no handle for the advertised replay. Give the caller a recoverable request ID before the effect, and commit the receipt with the effect. For `confirm`, the code itself can supply the stable handle. Repeat a successful confirmation after its hour has elapsed and require the original receipt. Confirming an unused expired code must still do nothing. [Feature creation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:170)

**3C-1.8. Two human decisions fall outside the proposed command map.** A failed completion gate accepts `retry`, while §4 gives `retry` only a parked-call target. A refused integration has a command, but its rejected intent is outside the three kinds listed in `inbox`. Give each a typed inbox item with its evidence and valid actions. Test both alongside a parked paid call after restart. From `relay inbox` alone, the person must be able to retry the final checks, authorise the particular push retry, or decide the paid call independently. [Gate actions](/Users/andrealaforgia/dev/relay-v3/src/relay/domain/story.py:276) · [Eligible integration retry](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:431)

**3C-1.9. The live usage query has already aggregated away facts the display promises.** `Features.usage_of` takes one feature and returns totals by role. A renderer cannot recover a project view by billed model and price-table version from that result. Build the live view from invocation records. Count a two-model call once in the project total, preserve missing counters, and show a whole-call cost at call level wherever its allocation is unknown. Test two billed models, two price-table versions and a late report beside an unchanged frozen summary. [Usage entry point](/Users/andrealaforgia/dev/relay-v3/src/relay/application/features.py:84) · [Aggregation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/final_checks.py:674)

**3C-1.10. Specify how the live session’s tool allowance is enforced.** A passphrase entered in a separate trusted terminal is reasonable for the stated single-host threat model. The missing part is how Claude gets precisely `show`, `inbox` and `prepare` while lacking a general command runner or direct database authority. Give the session a typed, project-bound interface and apply D-10 to this tool-enabled launch too. Exercise the actual session configuration. Reading and preparation must succeed; a deciding operation, passphrase rotation and paid `doctor --boundary` must be unavailable through it. The worker boundary tests cover a different tool set. [Host trust model](/Users/andrealaforgia/dev/relay-v3/docs/ARCHITECTURE.md:44) · [D-10](/Users/andrealaforgia/dev/relay-v3/docs/DECISIONS.md:31)

**3C-1.11. The final smoke can pass without exercising PO-3.** The proposed smoke runs approvals in a terminal and never starts `relay session`. PO-3 also requires a replacement session to be briefed from durable questions, answers, decisions and analysis versions. Put one session loss in the acceptance history. Have the session inspect a real gate and prepare an action, close it, start a fresh session, recover the outstanding context, and have the person confirm in their own terminal. Require one effective decision and the same receipt on replay. This can be deterministic in `make check`; the opt-in run can establish that the real interactive CLI uses the same interface. [PO-3](/Users/andrealaforgia/dev/relay-v3/docs/DECISIONS.md:9)

I would keep the lossy wake and periodic scan. Committed work gives the scan something durable to recover, and a deliberately dropped notification is a better acceptance test than asserting that `NOTIFY` was sent. I would also record live process diagnostics as deferred if 3c ships only `ledger`. A worker that cannot connect to PostgreSQL can emit a diagnostic without creating any ledger event. The specification identifies authorised diagnostic output separately. [Live log-tail scenario](/Users/andrealaforgia/dev/relay-v3/docs/SPEC.md:524)
