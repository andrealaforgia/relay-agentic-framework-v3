**I would keep the four build steps, but revise step 1 before implementation.** The integration-intent commit remains the right boundary for trunk. A push authorised before closure may still land and must be reconciled. The gaps are in how closure competes with story release, what authority a delivered command retains, and how interrupted work becomes runnable again.

### Findings

**S3-4.1 · BLOCKING for step 1 · Locking every existing story misses new stories and can deadlock release.** `release_next` holds the project lock before updating the selected story. A pause can lock that planned story and then wait to record its project event, while release holds the project and waits for the story. Sorting story IDs does nothing for this ordering. There is also nothing to lock when a feature has no stories. A roadmap published concurrently can create stories after the closure scan. Give closure a durable feature-level record and a common lock protocol with roadmap publication, release, gate decisions and intent authorisation. One simple option at this scale is a dedicated project lock acquired first by those short transactions. Test pause against both first-roadmap publication and release of a planned story, in both commit orders. **S3-4.2 · BLOCKING for step 1 · The working-story predicate cannot govern release, existing gates and the project slot.** A planned story fails `may_proceed` by definition, so the table as written cannot release the first story. Conversely, `decide` can settle an already-open gate without checking closure. There is a third concrete failure: cancel a feature whose story is `released`, then approve another feature. The selector skips the cancelled feature, but its story still occupies the database’s unique project slot. Restore v2.1’s transition-specific rules. Specify whether pause retains the slot, make cancel free it transactionally, and define the outcome of a fresh approval versus an exact receipt replay after closure. Test cancellation at an open gate with another feature waiting. **S3-4.3 · BLOCKING for step 1 · A successful claim needs a precise boundary, and direct calls must respect it.** A worker can claim a review command, pause before `prepare_review`, and resume after cancellation. A scripted caller can also call `prepare_review` directly with its existing capability. Today that operation checks the review cycle, exports the tree and issues a checkout receipt. `retry_integration`, `reopen_red`, review re-announcement and human gate decisions also need explicit treatment. Define which operations start work, which invalidate old authority, and which merely record work already authorised. If claim is the start boundary, commit a grant bound to the exact task and inputs. Closure-first must prevent a start through either route. Claim-first may finish under the stated in-flight policy. After cancel, a late red or green should leave audit evidence without creating a live successor. Exercise both orderings through the actual review API. **S3-4.4 · BLOCKING for step 1 · A refused delivery can be lost, and a matching cycle can revive obsolete work.** Publish a Builder command, pause, refuse its claim and empty Redis. Separately, a Builder command can still name the same red cycle after green has moved the behaviour to review. That command has finished its purpose. Persist the delivery disposition, re-announce eligible unfinished work under the same message ID, and check the state required by that particular command at claim. Apply reassessment per behaviour: one child’s unanswered question must neither release that child nor strand an eligible sibling. **S3-4.5 · BLOCKING for step 1 · The proposed integration request survives publication but can still strand its batch.** Resume a held batch, consume `integration.requested`, commit the fresh `running` batch, then kill the process. Replaying the same request returns `IN_PROGRESS`. Startup reconciliation scans integration intents, and this batch has none. There is also a race between claim and `integrate`: the latter selects the behaviour’s current cycle, so a delayed command for cycle A can start checks on cycle B. Keep the command, bind it to the held batch and expected cycle, and verify both when starting the new batch. Give an interrupted pre-intent batch a recoverable successor attempt under the same logical request. A scripted one-command handler is sufficient for this slice. Kill it after batch creation and prove restart leads to one settled intent or a recorded stale outcome. **S3-4.7 · BLOCKING for step 2 · Clearing a blocker does not establish that earlier work used the new answer.** Hold a passing batch based on decision D1. ### Answers to the four questions

| Question | Judgement |
|---|---|
| **Story-row closure** | Keep story rows for story-scoped blockers. Feature closure needs authority before the first story exists and across later roadmap revisions. Settle the locking and slot rules before step 1. |
| **`integration.requested`** | Yes. Make it executable through a scripted handler in step 1. Its exit test should demonstrate recovery after consumption and batch creation, as well as delivery after resume. |
| **One supersession gate for both correction routes** | Yes. The same PO authority should apply to both. Approval must name the exact old obligation and replacement contract, and every independent obligation must remain enforceable. |
| **Four review steps** | Yes. Keep the proposed order. Steps 2–4 can wait for their own rounds. Step 1 should establish the closure boundary, command-specific claim rules and recoverable integration request that they will use. |
