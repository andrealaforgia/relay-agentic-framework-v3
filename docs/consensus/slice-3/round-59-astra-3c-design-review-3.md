# Slice 3c: Astra's third review of the design

Provenance: written by Astra (gpt-6.2-astra via Codex) on 2026-11-27 in reply to `round-59-claude-3c-design-v3.md`; copied verbatim below. The last design round (D-8).

**I would fold eight amendments into the build contract and proceed under D-8.** V3 resolves the two ordinary hand-off failures from round two. A recorded review now has a recovery owner, and a failed green can make work runnable again while its Builder is still alive. The remaining step 1 issues arise at leadership handover, transport reconnection, and an explicit retry of a paid probe. I have no outstanding design finding against the worker-usage calculation in step 3.

**3C-3.1 · Step 1 · Reachable when leadership changes during a Git push.** The old leader has counted a send. Git returns a definite refusal after the new term opens. The blanket term check prevents the old leader from recording it. With trunk unchanged and no refusal on record, the new leader’s reconciliation can send again. If that send is also refused, the first send still counts as unanswered and the intent can remain pending instead of reaching the human inbox. Give each authorised send an identity under which its outcome can be recorded once across a term change. The current leader owns the workflow decision. Test with the former leader’s refusal arriving before the successor reconciles. Require one refused-push inbox item and no further send until the person retries. [Refusal handling](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:977) · [Reconciliation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:1008)

**3C-3.2 · Step 1 · Reachable when the control plane restarts against a different Redis.** A worker can pass its startup check on Redis A, remain alive, and keep reading A after the new leader starts publishing to Redis B. The installation namespace prevents cross-installation consumption. The startup check leaves this already-running worker stranded. Compare the marker’s term with PostgreSQL on a leadership change or transport reconnect, and give a running worker a bounded way to notice a stale marker while idle. An absent marker before the first `relay up` should report “waiting for the control plane”. Test the switch with the worker left running throughout. [Transport rule](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-59-claude-3c-design-v3.md:32)

**3C-3.3 · Step 1 · Reachable with two installations using different branches of one repository.** Both installations can legitimately have project `P`, behaviour `B1`, and attempt `1`. Their trunk refs and Redis streams differ, but both Builders publish to `refs/relay/attempts/P/B1/1`. The second Builder can have its correct result rejected as somebody else’s candidate. Give attempt refs an installation-unique identity and use it consistently in publication and recovery. Prove both first attempts survive, with neither installation buying a replacement call. [Attempt ref](/Users/andrealaforgia/dev/relay-v3/src/relay/git/checkout.py:130) · [Publication](/Users/andrealaforgia/dev/relay-v3/src/relay/application/tasks.py:696) · [Recovery lookup](/Users/andrealaforgia/dev/relay-v3/src/relay/application/reviews.py:469)

**3C-3.4 · Step 1 · Reachable through `doctor --boundary --retry`.** An `intended` row with no result also describes a probe that is still running. A second terminal must be able to distinguish that case from an uncertain attempt. Bind each explicit retry to the particular uncertain attempt and receipt the retry itself. Hold probe one open and replay its request. Then kill it, authorise one retry, lose that reply and replay the retry. The launch count should be one while the first probe is live and two at the end. The current test covers only replay of the original request. [Probe request contract](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-59-claude-3c-design-v3.md:38)

**3C-3.5 · Step 2 · Reachable through `prepare retry` followed by `set-aside`.** Prepare a retry for a parked call, then set the call aside directly. Today that closes the inbox item while leaving the assignment parked on the same invocation. The prepared code still names the latest invocation and can pass the service’s parked-work checks. Bind confirmation to the open inbox decision the person saw. In this order the unused code should return `stale`, leave the work parked and authorise no paid call. A newly requested reconsideration can have its own receipt. [Parked-call decision](/Users/andrealaforgia/dev/relay-v3/src/relay/application/invocations.py:740)

**3C-3.6 · Step 4, with a step 3 reporting consequence · Reachable on the second conversation turn.** The worker adapter uses one UUID for both the paid invocation and the provider session, disables session persistence, and rejects every MCP server in the start inventory. A hosted conversation needs a durable conversation ID, a fresh invocation ID for each paid turn, and an explicit session launch profile that verifies Relay’s server and tool list. Record the person’s input before launch and account for each turn once, including one before a feature exists. Test two turns in the same conversation, a lost terminal result on the second, and a live project cost view showing the known cost and the uncertain call. Leave the worker launch profile intact. [Adapter command](/Users/andrealaforgia/dev/relay-v3/src/relay/providers/claude.py:193) · [Inventory check](/Users/andrealaforgia/dev/relay-v3/src/relay/providers/claude.py:345) · [Assignment-bound invocation records](/Users/andrealaforgia/dev/relay-v3/src/relay/persistence/migrations/0015_invocations.sql:47)

**3C-3.7 · Step 4 · Reachable when the person answers an Interpreter note.** `note_question` records an open note, and `context` returns open notes. There is no operation that associates the person’s next answer with that note and closes it. Losing the session after the person types an answer can therefore make the next Interpreter ask it again. Let the host record the person’s actual turn against the named note, with conversational provenance. A binding workflow decision still goes through confirmation. Test closing the session after the answer is recorded but before the model replies. The new context should contain the question and answer and show that nothing is outstanding on that note. [PO-3](/Users/andrealaforgia/dev/relay-v3/docs/DECISIONS.md:9) · [Proposed context](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-59-claude-3c-design-v3.md:63)

**3C-3.8 · Step 4 · Reachable when a provider session cannot be resumed.** Keep the real-CLI continuation probe, but remove “session not delivered” as its prescribed failure outcome. V3 already requires a fresh session to recover from Relay’s records. That same path can serve the next turn with a new provider session, the same verified tool boundary and the durable conversation context. Delete the provider transcript between two turns and require the second turn to recover the analysis, the answered note and the prepared action. This also tests the recovery guarantee on a host where native continuation succeeds. [Design fallback](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-59-claude-3c-design-v3.md:56) · [Context requirement](/Users/andrealaforgia/dev/relay-v3/docs/SPEC.md:418)
