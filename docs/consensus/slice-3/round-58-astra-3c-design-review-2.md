# Slice 3c: Astra's second review of the design

Provenance: written by Astra (gpt-6.2-astra via Codex) on 2026-11-27 in reply to `round-58-claude-3c-design-v2.md`; copied verbatim below. Round two of at most three for this design (D-8).

**I would hold step 1 for three changes.** A returned result needs an owner when its worker disappears, a rejected green needs a route back to a live Builder, and startup recovery itself needs the control-plane term. All three are reachable in ordinary operation. The successful-build test in v2 can pass with all three still present.

The installation row, the retry bound to a particular refused intent, the typed inbox and the revised usage calculation answer their round-one findings. I have no further finding against step 3. I reviewed the design against the current services and checked the installed CLI’s help. I made no provider calls.

**3C-2.1 · Step 1 · Reachable after recording a review.** Stop QA after its reply commits as `returned` and before `submit`. The grant must survive because the result is known. Under v2, the periodic pass only takes effects belonging to the control plane, and the review’s next effect belongs to a worker. The assignment is still granted, so scanning wanted work cannot recover it. The same issue arises when QA stays alive but its apply returns `held` and the person later resumes. Specify who takes a known worker result in both cases. The simplest fit with 3b is to let the control plane recover database-only effects under the recorded grant. Require one effective submission, from the original checkout, with no second provider call. [Existing recovery](/Users/andrealaforgia/dev/relay-v3/src/relay/application/invocations.py:865) · [Existing review recovery test](/Users/andrealaforgia/dev/relay-v3/tests/integration/test_review_task.py:259)

**3C-2.2 · Step 1 · Reachable on the first build that fails green.** The Builder records `returned`, wakes the control plane, acknowledges its command and stays alive. The control plane then rejects the green. Below the attempt limit, today’s rejection path leaves the grant in place because the worker that called `apply` ordinarily prepares the retry itself. With the split, that loop has already ended. On a retryable refusal, return the still-owed assignment and arrange its announcement in the rejection transaction. At the limit, park it. Test with the original Builder alive and idle. The next delivery must buy exactly one new call and include the failed observation in its briefing. [Present retry loop](/Users/andrealaforgia/dev/relay-v3/src/relay/application/worker.py:247) · [Effect rejection](/Users/andrealaforgia/dev/relay-v3/src/relay/application/invocations.py:688)

**3C-2.3 · Step 1 · Reachable during overlapping startups.** Let the old control plane enter `Features.start` and wait on project A. It loses its lock connection. Its successor opens a new term and starts checks for B. The old process can then reach B’s startup cleanup, which interrupts running generations and revokes grants. Those transactions *end* work, so the proposed list of authorisation checks misses them. Fence startup cleanup in the transaction that selects and changes the work. Also state how a new leader takes over a started control-plane effect if the old leader’s separate recovery-session lock still looks live. Exercise both with the old process alive; B’s new generation must survive. [Startup loop](/Users/andrealaforgia/dev/relay-v3/src/relay/application/features.py:105) · [Completion cleanup](/Users/andrealaforgia/dev/relay-v3/src/relay/application/final_checks.py:386) · [Effect ownership](/Users/andrealaforgia/dev/relay-v3/src/relay/application/invocations.py:585)

**3C-2.4 · Step 1 · Reachable with two bootstrap files.** A control plane and worker can point at the same PostgreSQL installation and different Redis databases. Both see the correct installation row, both can report healthy connections, and the worker never sees the control plane’s commands. Conversely, two installations sharing Redis can use the same project name and role, which today gives them the same stream and consumer group. Bind transport to an installation identity, namespace the streams and have `doctor` check that the processes agree. Prove the mismatched pair is diagnosed and the shared-Redis pair cannot acknowledge each other’s deliveries. [Stream and group selection](/Users/andrealaforgia/dev/relay-v3/src/relay/application/worker.py:128)

**3C-2.5 · Step 1 · Reachable through `doctor --boundary`.** Kill the command after it launches a paid probe and before it records the boundary result. Repeating the same request finds no fresh pass and can buy the probe again. The proposed journal recovers a request ID, but the current suite calls the adapter directly and records its result afterwards. Give each paid probe a durable request and attempt before launch. A replay should return the known result or expose the uncertain attempt for an explicit retry. Test this with the stand-in CLI and a launch counter. [Suite launch](/Users/andrealaforgia/dev/relay-v3/src/relay/providers/boundary_suite.py:469) · [Pass recording](/Users/andrealaforgia/dev/relay-v3/src/relay/application/boundaries.py:30)

**3C-2.6 · Steps 1–2 · Reachable from any command naming a project-local subject.** The installation now tells a process *how* to serve every project. It still needs a rule for *which* project `feature start`, `status`, `prepare` and `session` address. Register two branches of the same repository, each with an `F1`, and run the command from outside either checkout. Define an explicit project selector and refuse an ambiguous default. Store the resolved installation and project in the request journal so replay does not reinterpret the original command in a different directory. A session bound to A must also refuse `show` and `prepare` for an item belonging to B, even when given its valid ID.

**3C-2.7 · Step 2 · Reachable through `prepare resume`.** Pause F, prepare its resume, resume it directly, then pause it again for a different reason. The old code still names the same project, feature, action and arguments, and F is paused again. Confirming it would clear a pause the person never reviewed. Bind resume to the particular pause event or closure revision and compare it under the feature lock. Require `stale` for the unused old code and the original receipt for an exact replay of a resume that already took effect. [Current closure decision](/Users/andrealaforgia/dev/relay-v3/src/relay/application/stories.py:667)

**3C-2.8 · Step 4 · Reachable on the first `relay session`.** The installed Claude Code 2.1.331 describes `--output-format` as available only with `--print`. The worker obtains its structured start inventory on that path. V2 promises the same check for the interactive session without identifying how Relay receives it. Establish the supported channel on the actual interactive launch, or make Relay host the conversation through an interface that exposes the inventory. The acceptance test should exercise that launch, read a real item through MCP and prepare one action. Testing the server’s tool list alone cannot establish what else the client loaded. [Worker launch](/Users/andrealaforgia/dev/relay-v3/src/relay/providers/claude.py:209) · [Proposed session check](/Users/andrealaforgia/dev/relay-v3/docs/consensus/slice-3/round-58-claude-3c-design-v2.md:55)

**3C-2.9 · Step 4 · Reachable when the Product Owner loses a conversation mid-analysis.** The new `context` history recovers a prepared approval. PO-3 also promises that an analysis version and an Interpreter question survive as they are produced. The proposed tool list has no operation to record either, and `context` contains no analysis version. Give the Interpreter a narrow way to record those as model-authored material, with human confirmation still required for a decision. Close the session after an analysis revision and an unanswered Interpreter question, before any action is prepared. The replacement session should recover both. If discovery is deliberately deferred, record that as partial delivery of PO-3.
