**The build still permits a second push after Git’s refusal is on record, and a former leader can mark an outbox message delivered to the wrong Redis.** Both are reachable through `relay up` during the handover this step is meant to support. I would fix those before closing 1a.

I reviewed `f02815f`. The checkout differs from it only by the submission document. I independently ran 26 focused unit cases and two in-memory process-loop checks. The reported full-suite result is the author’s. I did not rerun the PostgreSQL, Redis, Docker or paid-provider suites.

**3C-S1A-1.1 · A recorded refusal can still be followed by another push. Reachable through `relay up`.** Let the successor finish `_count_what_was_heard` while the old send has no answer. The former leader then commits `heard='refused'` and is fenced before it can update the intent. The successor’s `count_the_send` checks `integration_intents.refusal`, which is still null, and authorises another send. Make the final send-authorisation statement check for a recorded refusal under the intent’s serialisation rule. Put the refusal *between* the scan and authorisation in the regression test. The remote should see one send and the person should see one refused-push item. [Reconciliation scan](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:1071) · [Send authorisation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:886)

**3C-S1A-1.2 · Shutdown can lose the refusal the former leader actually heard. Reachable through `relay up`.** After Git raises `RemoteRejected`, `_heard` still has to acquire a connection and commit. Shutdown cancels the project task and can interrupt that write. The successor then sees an unanswered send, even though Git supplied a definite answer. Once the answer is known, let its observation commit across graceful shutdown and drain that write before closing the pool. Test by holding the write, stopping the process, and then releasing it. This is a different history from 1.1, where the observation already committed. [Recording the refusal](/Users/andrealaforgia/dev/relay-v3/src/relay/application/integration.py:919) · [Process shutdown](/Users/andrealaforgia/dev/relay-v3/src/relay/processes.py:129)

**3C-S1A-1.3 · The outbox publisher can act after its term ends. Reachable through `relay up`.** `_publish_next` selects an unpublished row, appends to Redis and sets `published_at` without checking the term. With the successor on Redis B, the former leader can deliver a row to Redis A and mark it published in their shared database. The new publisher skips it. Wanted assignments get another announcement, but that mechanism does not cover every outbox message. Fence the publisher transaction. The audit requested by the contract should also cover the separate writes that mark an invocation `applied`, release a started effect and allocate a build attempt. A gate check in the preceding transaction cannot fence those writes. [Outbox publisher](/Users/andrealaforgia/dev/relay-v3/src/relay/persistence/outbox.py:63) · [Invocation completion and cleanup](/Users/andrealaforgia/dev/relay-v3/src/relay/application/invocations.py:529) · [Attempt allocation](/Users/andrealaforgia/dev/relay-v3/src/relay/application/tasks.py:679)

**3C-S1A-1.4 · One unavailable repository can prevent the whole installation from starting. Reachable through `relay up`.** Leave a returned build in A awaiting publication, make A’s remote unavailable, and restart with B ready. `Features.start` runs A’s full pass inline. The failed ref lookup escapes invocation recovery before the independent project loops or the Redis marker start. Repeated restarts can fail at the same point. Preserve the startup cleanup for each project and let its recoverable Git failures retry independently. The acceptance condition is that B reaches trunk while A’s returned build remains available for recovery. [Startup](/Users/andrealaforgia/dev/relay-v3/src/relay/processes.py:103) · [Sequential project passes](/Users/andrealaforgia/dev/relay-v3/src/relay/application/features.py:112) · [Build ref lookup](/Users/andrealaforgia/dev/relay-v3/src/relay/application/tasks.py:716)

**3C-S1A-1.5 · A worker can launch further calls after its transport changes or it receives SIGTERM. Reachable through `relay worker start`.** The marker and stop flag are checked outside the loop over projects. One `serve_once` can also process several deliveries, and one delivery can buy a retry. If A’s call takes longer than thirty seconds, B can start under the old transport check. In an in-memory run I set `stop` during A and observed B dispatched with `stop` already set. Check stop and transport eligibility before each new admission, including retries, and invalidate the transport check on reconnect. Test with the worker alive across the Redis switch and with a second delivery already read. [Process loop](/Users/andrealaforgia/dev/relay-v3/src/relay/processes.py:186) · [Delivery loop](/Users/andrealaforgia/dev/relay-v3/src/relay/application/worker.py:145)

**3C-S1A-1.6 · A worker that loses its ownership connection can keep consuming commands forever. Reachable through `relay worker start`.** Drop only the worker’s advisory-lock connection. Its pooled connections and Redis can still work. `claim` correctly refuses the dead identity, but the serving loop acknowledges the delivery and carries on under that same identity. With one worker of the role, repeated announcements produce repeated refusals. Have the process exit visibly or enrol a fresh worker identity before consuming again. An invocation left under the old identity must still follow the existing uncertain-call recovery rule. [Claim refusal](/Users/andrealaforgia/dev/relay-v3/src/relay/application/assignments.py:536) · [Acknowledgement](/Users/andrealaforgia/dev/relay-v3/src/relay/application/worker.py:149)

**3C-S1A-1.7 · A paid call can be admitted under an obsolete policy statement. Reachable through `relay worker start` when the installation policy changes.** The CLI polls the statement once a second. Admission checks a boundary digest built from the cached text. A policy change committed before admission can therefore leave the previous pass authorising the call. If the polling task fails, its last value can survive longer. Compare the statement revision used to prepare the digest with the installation revision in the admitting transaction. A deterministic test can commit the change between preparation and admission and require zero launches. [Policy poll](/Users/andrealaforgia/dev/relay-v3/src/relay/cli/main.py:61) · [Admission callback](/Users/andrealaforgia/dev/relay-v3/src/relay/application/worker.py:228)

**3C-S1A-1.8 · Listener failure can strand leadership. Reachable through `relay up`.** If acquiring the listener connection or executing `LISTEN` fails, `listening_now` is never set. I reproduced the parent remaining blocked even after setting its stop event. If the listener dies later, the timer preserves progress, but notifications remain unavailable until restart. Supervise the listener task. At startup, either retry or exit and release leadership; after startup, reconnect and rescan. [Listener lifecycle](/Users/andrealaforgia/dev/relay-v3/src/relay/processes.py:80)

**3C-S1A-1.9 · The effective profile can authorise an uncapped paid call. Reachable through `relay worker start`.** A profile with no `budget_usd` resolves to `None`, and the adapter omits `--max-budget-usd`. The process fixture uses exactly such a profile. The contract calls for a maximum per call. Require a finite positive effective cap before launch, or supply a documented capped default. Exercise it from installation settings through the stand-in CLI’s actual arguments. [Profile resolution](/Users/andrealaforgia/dev/relay-v3/src/relay/runtime.py:101) · [CLI arguments](/Users/andrealaforgia/dev/relay-v3/src/relay/providers/claude.py:226)

**3C-S1A-1.10 · The handover test can terminate unrelated database sessions. Reachable through `make check`; test-suite finding.** The process test terminates every other backend visible to it that holds a granted two-key advisory lock. It does not identify the test installation’s lock or even filter on the current database. On a shared PostgreSQL server it can interrupt another Relay or an unrelated application wherever the test account has permission. Select the exact lock holder for this fixture and assert there is one before terminating it. Run the test beside a second lock holder and require that connection to survive. [Handover test](/Users/andrealaforgia/dev/relay-v3/tests/integration/test_processes.py:210)

The process test does establish one Builder call, one effective green and completion following leadership replacement. I would keep that test. Its handover occurs after roadmap approval, so the refusal, outbox and active-worker histories above each need their own ordering.
