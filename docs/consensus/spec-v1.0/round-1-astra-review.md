## 1. FINDINGS

**I challenge version 1.0 as an implementation contract.** The choice of PostgreSQL as authority, Redis as transport and deterministic code as gatekeeper is sound. The blocking gaps concern what that gatekeeper can know. As written, Relay could accept a fabricated test report, repeat a paid invocation after a crash, or integrate a revision that nobody reviewed, while appearing to satisfy the workflow.

`BLOCKING` means the contract needs settling before implementing the affected slice. It need not delay independent slices.

| ID | Severity | Claim and specification evidence | Why it matters | Proposed resolution |
|---|---|---|---|---|
| F1 | BLOCKING | §§2, 5.4, 6C and 14 require a test to fail “for the intended reason”. The specified inputs include an “expected failure explanation” and output. Neither establishes which assertion ran or what it observed. | A worker can supply a convincing explanation for a collection failure, a broken fixture or an unrelated assertion. Matching stderr rewards the appearance of evidence. | Have the Verifier declare an observable predicate and the admissible baseline failure **before** execution. A trusted runner records setup, observation, assertion identity and outcome. Reject collection errors, missing tests, skips, timeouts and unexpected failures. The Verifier owns the judgement that the predicate expresses the behaviour. |
| F2 | BLOCKING | §§5.4, 6C and 32 require running a newly written test “against an identified baseline” and an “independently verified red state per behaviour”. The baseline predates the test. §§5.4 and 6C repeatedly specify the “first” behaviour. | A baseline SHA alone cannot reproduce the run. Later behaviours could inherit an earlier red, or require Codex despite the Claude-only promise. | For **every** behaviour, identify the production baseline, separately mounted contract bundle, runner image and execution manifest. Use an independent runner in both provider modes. Record peer review separately. A material contract or baseline change requires fresh evidence. |
| F3 | BLOCKING | §§5.5, 14 and 21 restrict the Builder to “production implementation”, require “smaller red-green-refactor cycles”, and protect the approved acceptance test. They leave ownership of unit tests, fixtures, runner configuration and test discovery open. | Banning all test writes impedes TDD. Protecting only the acceptance-test file lets a Builder disable its collection or replace a fixture underneath it. | Give the Builder production and unit-test paths. Put the approved acceptance bundle, fixtures, oracle, invocation and mandatory regression policy under separate ownership. A Verifier amendment creates a successor contract and reopens red. Report inner-loop TDD only to the extent it was observed. |
| F4 | BLOCKING | §§10–11 say “Use a transactional outbox” and “Acknowledge queue messages only once work results are durable”. They omit publication order, duplicate identity, lost broker entries and the acknowledgement condition for a long-running task. | A crash after Redis accepts a message can publish it twice. A Redis restore can lose a command already marked published. An early acknowledgement can strand a task. | Commit the task, event and outbox row together. Publish with a stable logical ID, then mark the row sent. Recover unfulfilled tasks from PostgreSQL even if Redis has no pending entry. Acknowledge only after a durable result or explicit durable disposition owns recovery. |
| F5 | BLOCKING | §§3.2, 11 and 23 specify a “lease/fencing token” and say to “Discard stale results”. No authority, expiry clock or atomic acceptance rule is specified. | A disconnected worker can return after expiry but before reassignment. Checking only whether a newer attempt exists admits that result. Redis pending ownership can also change while a worker is healthy. | Let PostgreSQL issue monotonically increasing generations using database time. Match project, task, worker, generation, unexpired lease, current input version and eligible run state in the result transaction. Apply the same ownership check to renewal. Redis claiming grants delivery only. |
| F6 | BLOCKING | §11 recognises calls that “might have completed and incurred cost before the response was lost”. §29.11 expects duplicate delivery to prevent “duplicate completion or side effects”. These guarantees differ across the uncertain-call window. | If the provider accepted a call and the response was lost, an automatic retry can spend twice. Refusing all retries without recording why leaves apparently stuck work. | Promise one canonical completion. Persist invocation intent before calling. Recover a known receipt if supported. Otherwise mark the effect `unknown`, expose possible spend and require an explicit retry decision. Test both a known durable result and an unknown outcome. |
| F7 | BLOCKING | §3.2 says remote workers “need only broker/control-plane connectivity”. §13 allows an “authorised Git remote or versioned artefact mechanism”. It does not choose a reachable source or specify how another worker fetches an unpublished candidate. | A commit hash in Redis cannot transfer Git objects. The Builder can disappear with the only copy of the revision awaiting review. | Make source exchange an explicit deployment contract. My default is a Git endpoint reachable through the control-plane deployment, with pinned fetchable refs, immutable candidate refs, path validation and retention through the evidence lifetime. |
| F8 | BLOCKING | §§6D, 13–15 call for checks “against the exact integrated revision”, optimistic concurrency and reviews bound to “immutable revisions or patch hashes”. They do not define when trunk moves or what survives a changed base. | A reviewed patch can produce different behaviour after rebase. A crash between updating Git and recording integration can cause a second integration or a false failure. | Construct the final candidate on the observed trunk head. Run checks and reviews on its exact SHA. Persist integration intent, then conditionally advance trunk from the expected head to that SHA. Reconcile the intent against Git on restart. A changed base produces a new candidate and fresh gates. |
| F9 | BLOCKING | §§7, 12, 16 and 24 require the “same artefact version”, a “precise story version and evidence snapshot” and reopening “only affected work”. They define neither version identity nor dependency tracking. | Both peers can say “accept v2” about different bytes. An answer amended after QA could leave a green dashboard and an actionable stale approval. | Give every immutable artefact a project-scoped identity, revision, content digest and explicit dependency references. Bind responses to the exact proposal and approvals to a manifest of evidence, reviews, decisions and policy. Reject stale actions transactionally. Keep superseded records readable. |
| F10 | BLOCKING | §7 excludes automatic agreement at the round cap. §29.7 says “until the challenge is resolved or explicitly escalated”. §§7 and 15 do not identify who may close a disputed finding or whether reservations count as acceptance. | Escalation could satisfy the scenario while violating the consensus rule. A Builder could obtain closure by rewording a finding or submitting a cosmetic revision. | Make escalation a blocked state with a named decision owner. Require explicit acceptance from every required participant on the current version. Reservations may remain only as recorded non-blockers. The issuing review authority verifies remediation. Any permitted override records the actor, scope and reason separately from consensus. |
| F11 | BLOCKING | §§3.3, 4 and 21 require “role-scoped permissions” while mapping both Verifier and Builder to `alf-atdd-developer`. “Restricted to” describes intent, without an enforcement contract for either CLI. | A role prompt, an installed agent file or a worker-advertised capability cannot establish which files, tools, credentials or sessions an invocation can access. | Enforce authority outside both CLIs. Use isolated identities and fresh role contexts, read-only inputs, constrained outputs and a trusted importer. Disable or mediate side-effecting tools. Fail closed when an adapter cannot provide the configured profile. Record the actual definition bytes, effective restrictions and provider configuration. |
| F12 | BLOCKING | §§5.4, 11, 14 and 21 say workers report evidence and run untrusted commands in “sandboxed environments without unrestricted access to home directories”. The trust boundary between repository code, runner, adapter and credentials is unspecified. | Repository tests can forge a report, read a mounted credential, contact an external service or exhaust the host. Giving the model access to a Docker socket defeats filesystem restrictions. | Specify the supported threat model. Separate the credential-bearing provider adapter, source importer, test subject and evidence recorder. Use disposable, resource-limited execution with denied egress and no host credentials, sockets or writable evidence channel. Permit only a narrow observation channel to the trusted harness. |
| F13 | BLOCKING | §§1, 8–9 and 20 promise Claude-only operation, make cross-provider review optional, and illustrate `problem_analysis: required` with Codex `enabled: auto`. A valid Claude-only preset and the effect of an enrolled peer disappearing are left implicit. | A clean Claude-only project could block at discovery. Conversely, losing a required reviewer could silently turn a two-provider gate into a one-provider gate. | Supply explicit Claude-only and dual-provider presets. Freeze effective policy for each gate. Record `disabled`, `unavailable`, `substituted` and `completed` separately. Only an authorised policy change can release a required unavailable peer gate. |
| F14 | BLOCKING | §§6D–E, 16–17 and 25 put integration before story approval, offer `reject`, `pause` and `cancel`, and require “clearly defined effects on in-flight work”. No such effects are defined. | Rejecting an already integrated story cannot safely imply resetting trunk. A worker can finish while a human cancels, or a stale approval can release the wrong next story. | Define approval as acceptance of the story and permission to release dependent work. Specify the integration commit point. Pause stops new dispatch and integration authorisations, cancel fences outstanding attempts, and both reconcile already-authorised external effects. Rejection creates an explicit remediation or revert decision. |
| F15 | BLOCKING | §§17, 20 and 22 require enforcement of a GBP budget while permitting unknown usage and saying estimates are not “precise hard guarantees”. | Two concurrent calls can each pass a remaining-budget check. A subscription session with unknown cost can appear free or defeat a monetary ceiling. | Reserve known upper bounds atomically before dispatch, settle observed usage separately, and retain reservations for uncertain calls. Offer call, story and time caps independently. If a hard monetary bound is requested, admit only work with an enforceable upper bound. |
| F16 | BLOCKING | §§10, 18, 21 and 25 require sender validation, “safe export” and human approval. The envelope’s `sender` is supplied data. The spec does not bind worker results, dashboard reads or approval commands to authenticated principals. | A worker could impersonate a reviewer or Product Owner. Redacting the live tail alone leaves secrets in persisted transcripts, artefacts or exports. | Enrol workers with project and role grants. Derive identity server-side. Give human approvals a separate authenticated route. Authorise artefact reads and event subscriptions by project. Filter before persistence and streaming, cap output and define retention. Keep raw provider streams out of the ledger. |
| F17 | NON-BLOCKING | §§8, 18–19 and 30 combine routing calibration, broad tracing, operations UI, two providers and remote operation before the first full behaviour. §§18 and 31 ask to preserve earlier dashboard behaviour “where practical”. | The team can demo infrastructure and agent conversations for several milestones without proving one useful behaviour. The verified predecessor has no web dashboard, so dashboard compatibility has no established baseline. | Lead with one real red-to-approved behaviour. Use the separate reuse assessment for concrete contracts worth preserving. Defer calibration, broad telemetry and interactive operations until their underlying operations work through the CLI. |

## 2. PRODUCT OWNER DECISIONS

| Decision | Options and trade-off | Recommended default |
|---|---|---|
| What does story approval authorise? | Approval before integration holds changes off trunk during a human pause. Approval after integration preserves short integration intervals but rejection may require a forward fix or revert. Deployment is a separate decision. | Approve **after** verified integration. Gate the next dependent story. Keep incomplete user-visible behaviour behind a project-controlled flag where needed. |
| Which machines and repositories are trusted? | Enrolled operator-controlled workers can host adapters and runners under a defined isolation boundary. Accepting arbitrary worker operators requires stronger isolation and independent verification of their reports. Supporting hostile multi-tenant workloads changes the deployment substantially. | One Product Owner, enrolled trusted hosts, untrusted repository contents and agent output. Run authoritative tests on a controlled runner. A remote reviewer may review the candidate without authority to attest its execution. |
| What counts as an admissible first acceptance contract? | A bounded family of black-box contracts permits mechanical red validation. Arbitrary repository frameworks offer broader adoption but need runner-specific outcome adapters and a policy for ambiguous failures. | Support one external process or CLI behaviour with structured observation first. Admit another framework when it can distinguish assertion failure, setup failure and non-execution. Escalate ambiguous evidence. |
| When is independent review mandatory, and who may accept risk? | Mandatory cross-provider review improves separation and blocks work during outages. Best-effort review preserves availability. Permitting security overrides changes what “mandatory” means. | Claude-only is first-class. Dual-provider projects explicitly select required stages. Allow recorded substitution only at best-effort stages. Keep unresolved high or critical Sentinel findings blocking by default, with no v1 override. |
| What happens after an unknown paid call? | Automatic retry favours throughput and accepts duplicate spend. An operator decision preserves budget control and may leave work paused. A strict GBP cap excludes invocations with unbounded or unknown price. | Pause on unknown effect. Show the reservation and possible duplicate cost before an authorised retry. Use enforceable call and time limits for subscription sessions. |
| Which Git and CI environment must the first release support? | A Relay-managed Git endpoint and controlled runner give a tractable conditional integration protocol. Existing protected remotes and mandatory hosted CI require provider-specific status, credential and merge semantics. | Prove the protocol with a managed Git endpoint. If the first real project requires hosted branch protection, select that host and include its required CI in the first integration slice. Relay must leave integration blocked wherever it cannot honour branch policy. |

## 3. SMALLEST VIABLE ARCHITECTURE

**Topology.** Use one control-plane process for the authenticated API, scheduler, FSM, outbox publisher, recovery loop and integration controller. Use PostgreSQL and Redis as separate services. Run one enrolled worker daemon per host. The daemon invokes a provider through a role-specific adapter. A separately isolated execution service on a trusted host runs the acceptance harness and regression jobs. The CLI and a thin read-only dashboard use the same API. The Claude Code entry point can open a run or surface a pending question through that API. Human answers and approvals require a human identity unavailable to agent tools.

**PostgreSQL.** The following are logical tables. Small deployments can keep bounded artefact bytes in PostgreSQL and use Git for source. The controlling constraint is that a canonical transition, its ledger entry and its outgoing work commit together.

| Tables | Key columns and constraints |
|---|---|
| `projects`, `runs`, `stories`, `behaviours` | Project and parent IDs, state, current version, policy version. Project-scoped foreign keys prevent cross-project references. Conditional updates require the expected version. A partial unique constraint enforces the initial one-active-implementation-story policy. |
| `events`, `outbox` | Event ID, project sequence, type, actor, subject/version, correlation, causation and immutable payload refs. Unique `(project, sequence)` allocated under a project lock in commit order. Outbox carries stable message ID, destination, payload, publish state and retry time. Domain writers cannot update or delete ledger rows. |
| `workers`, `tasks`, `attempts`, `receipts` | Enrolled principal and granted pools, last heartbeat, task operation key, input manifest, state, current worker, generation and expiry. Unique logical operation per project and input version, unique `(task, generation)`, at most one canonical task result. Receipts deduplicate authenticated submissions by operation key and reject conflicting payloads. |
| `artefacts`, `artefact_dependencies` | Project, logical ID, revision, media type, byte length, SHA-256 and bounded bytes or immutable Git ref. Unique `(project, logical ID, revision)`. Hash the stored bytes. Anchor proposal identity to the exact revision as well as its digest. Dependency edges point to immutable revisions. |
| `proposals`, `responses`, `findings`, `decisions`, `approvals` | Exact subject or snapshot ref, required participant set, authenticated author, round, disposition and blocking status. Stable finding ID with append-only lifecycle records. At most one effective response per participant and proposal revision. Approvals require the current snapshot and authorised principal. |
| `changesets`, `executions`, `integration_intents` | Repository, base and candidate SHAs, immutable refs, contract and runner digests, selected and executed tests, outcomes, evidence refs, review snapshot and integration state. Unique integration operation per candidate and expected head. Only the trusted runner identity can submit gate-bearing executions. |
| `invocations`, `reservations` | Task attempt, provider, resolved model/profile, role-definition digest, effect state, optional provider receipt, nullable usage, price-table version, estimate, actual billing if known and reserved bound. Reserve under the budget owner’s row lock. Preserve unknowns through aggregation. |

**Transport and recovery.** Use a command stream per project and eligible capability pool, with one execution consumer group per stream. Only interchangeable workers belong in a pool. QA and Sentinel get separate addressed tasks, even when they review the same SHA. Use a project event stream with a distinct group per independent subscriber. The dashboard reads the ledger through the API and can resume by project sequence. Workers submit results through the authenticated API, which records them and emits the resulting events through the outbox.

The single publisher reads committed unsent rows, appends to Redis, then records successful publication. A crash between those steps republishes the same logical message ID. A reconciler periodically reannounces eligible unfinished tasks with no live owner, including after broker data loss. Delivery order never overrides the database state or input version. Inspect and reclaim abandoned pending entries. A healthy database lease prevents a reclaimed entry from starting a second execution. After a durable terminal result, supersession or explicit parked failure, redelivery can acknowledge the entry without calling the provider. Malformed messages get a bounded diagnostic and a durable dead-letter disposition. Replay reads the ledger into new projections with external-effect dispatch disabled. Redis documents acknowledgement and pending-entry claiming as consumer-group operations. [Redis XACK](https://redis.io/docs/latest/commands/xack/) and [Redis XAUTOCLAIM](https://redis.io/docs/latest/commands/xautoclaim/)

**Leases and external effects.** Claim and renew through the control plane. A claim locks the task row, checks eligibility and advances the generation. A heartbeat extends only a still-valid lease. Result acceptance checks all F5 conditions while holding the row lock, then writes the result, transition and outbox together. A stale attempt may leave a quarantined blob or a late usage receipt. It has no authority to change the candidate, gate or canonical result. Persist provider-call intent before launch. On lost contact after intent, park the call unless the adapter can recover its outcome. An expired lease makes work recoverable; it does not make repeating a paid call safe.

**Artefacts and consensus.** Upload bounded bytes through the control plane, verify their digest and make the reference readable before publishing a message that contains it. Retain approved evidence and Git objects for the configured audit lifetime. A proposal manifest freezes content, dependency revisions, required reviewers and policy. Each peer responds to that manifest. On revision, retain finding identities and history, invalidate prior acceptances and request explicit acceptance of the successor. A four-round cap produces an open escalation. A changed human decision invalidates dependent manifests, pending work and approval links through recorded edges. Previously integrated code remains an auditable fact and may need a corrective story.

**Git exchange and integration.** Serve a bare Git repository through the control-plane deployment. A worker fetches a named, pinned base ref, verifies its SHA and creates a disposable checkout. Its trusted adapter returns a commit through an attempt-scoped staging ref. The importer validates ancestry, tree changes, file types, protected paths and project scope before creating a retained immutable candidate ref. Reviewers and runners on other machines fetch that ref and verify its SHA. Provider processes receive neither trunk credentials nor ambient Git helpers.

The controller persists a short-lived integration operation only after checking current gates and run state. It verifies fast-forward ancestry and asks the remote to advance **from the explicit expected old SHA to the reviewed candidate**. An intervening trunk change rejects the operation. On restart, inspect the protected ref and its history to distinguish an already landed candidate from a pending or conflicting update. Pause and cancel stop new integration authorisations. An operation already past authorisation is reconciled and disclosed to the Product Owner. Hosted CI, where required, must attest the same SHA, including any host-created merge result, before Relay declares completion. [Git conditional ref updates](https://git-scm.com/docs/git-push)

**Executable red and green.** Start with a CLI fixture whose baseline returns the wrong business value on a valid request. The Verifier approves the input, expected value, admissible baseline observation, assertion ID and execution manifest before either run. A recorder outside the subject sandbox launches the pinned build, makes the request and evaluates the predicate itself. It distinguishes a successful launch and wrong business value from failure to launch. Red requires the selected assertion to execute and produce the registered mismatch. Green requires the same contract to execute and pass on the candidate, with the required regression set collected and passing. Missing, skipped or unexpectedly retried tests cannot silently count as passes. Run a fresh trusted checkout for the final checks. A model-produced JUnit file or success message has no gate authority. This establishes a reproducible behavioural difference. Whether the chosen example captures the customer’s need remains a Verifier and Product Owner judgement.

**Deliberate reductions.** Start with one active story, one contract family, two explicit provider presets, bounded PostgreSQL artefacts, one Git integration route and a single scheduler/publisher. Deliver ledger-backed dashboard views before interactive operations. Defer adaptive model routing, native session continuation, multiple selectable Git backends, full-stack tracing and searchable log export. These reductions need Product Owner agreement wherever §32 makes a capability a release condition. Distributed execution, genuine provider smokes, enforcement of review gates and failure recovery remain release evidence.

## 4. SLICE ORDER

Section 30 puts a real red test at milestone 4, integration at 5, mandatory reviews at 6 and human gates at 7. Yet milestone 1 claims crash recovery while milestone 9 introduces its leases and deduplication. I would move each failure case into the first slice that creates the corresponding effect. Start with real PostgreSQL, Redis, Git and runner processes. Script provider *responses* for deterministic acceptance tests. Use separate genuine CLI smokes to establish that each adapter can perform its assigned role. Never have a fake provider supply the test outcome.

| Slice | Executable acceptance test | §29 coverage |
|---|---|---|
| 1. One behaviour demonstrably changes | Through the CLI, submit a fixed story and contract against a tiny executable repository. Observe no Builder task on a setup error, skipped test, already-green baseline or forged pass report. Supply the registered red, change production code, and require the same externally observed assertion plus regressions to pass. An attempted contract edit is rejected. | **4, 5** for the supported contract family. |
| 2. One reviewed change lands once | Release QA and Sentinel tasks on the same candidate. Hold each at a barrier to demonstrate independent dispatch. A blocker from either prevents integration. A successor SHA requires fresh reviews. Advance trunk concurrently and observe stale-base rejection. Inject crashes after Redis publish and after Git update, redeliver, and assert one canonical result and one trunk advance. A failed required CI check holds the gate. | **6, 11** for recoverable effects. The unknown paid-call case is exercised in slice 5. |
| 3. One Claude-only story reaches its human boundary | Start through the Claude entry point with Codex absent. Produce a blocking question, persist its answer, approve the versioned roadmap and complete a two-behaviour story through slices 1–2. Restart all Relay processes at the story gate. Assert identical evidence refs, unchanged invocation count and no second-story dispatch. Try stale approval, request changes, rejection and approval in separate runs. Pair the scripted journey with a genuine Claude role/loading smoke. | **1, 3, 8, 14**, with the autonomy branch of **8** in slice 6. |
| 4. Two providers disagree across machines | Enrol a second physical host with no shared checkout. Run a genuine Codex read-only review smoke on a fetched immutable ref. In the deterministic journey, challenge a specific analysis, revise it and attempt acceptance using the old digest. Exercise both resolution on the new version and exhaustion of four rounds. Escalation must leave consensus open. Disconnect a required peer and observe an actionable block. | **2, 7**. |
| 5. Remote work survives loss of ownership | Partition host A after it claims a task. Expire its lease using controlled database timing, recover the pending task on B and submit A’s late result both before and after B returns. Neither late submission advances state. Repeat with a durable result, an empty restored broker, and a provider that accepted a call but lost its reply. Assert no automatic second paid invocation. | **10, 11**, including the explicit unknown-effect outcome. |
| 6. Autonomy stays within its authority | Opt in for one additional story. Race two dispatches for the final reservation. Assert that only admissible work starts and that a pending decision or mandatory finding independently prevents release. Change an upstream answer while work is in flight. Assert the dependent snapshot is reopened and stale approval fails. Exercise pause, cancel, timeout, rate limit and malformed reply with visible dispositions. | **8, 9**. |
| 7. The Product Owner can inspect what happened | Drive the dashboard from the preceding run. Reconcile roadmap, conversations, current blockers and ledger with the CLI. Mix known token counts, estimated GBP, unavailable usage and an actual billing fixture. Assert correct grouping by provider, model, role and story, with unknowns visible. Rebuild projections and compare results while counting zero external calls. | **12**. |
| 8. An authorised operator can tail a worker | Enable the optional tail during a running task. Emit a seeded secret split across output chunks and a permitted diagnostic. Assert the diagnostic arrives, the secret is absent from stream and retained data, and a principal from another project cannot subscribe or export. Verify reconnect and disable. | **13** when enabled. If deferred, record the scenario as outstanding. |

Use the §26 failure list as an executable coverage index across these slices. Each injected fault should name its expected durable state, ledger event, permissible next action and external-effect count. A passing process exit or a screenshot of a blocked badge would miss the failures that matter here.

## 5. TOP RISKS

| Risk | Earliest cheap test |
|---|---|
| **1. Relay certifies the colour of a report instead of a change in behaviour.** | Before adding a provider, feed the runner four cases with the same apparent failure text: wrong business value, failed setup, zero collected tests and forged output. Only the observed business mismatch may unlock the Builder. |
| **2. A retry repeats paid work or lets an expired attempt win.** | Put a counting provider stub behind a barrier immediately after it accepts a call. Kill the worker there, redeliver, expire its lease and submit a late response. Require one call, an explicit unknown effect and zero accepted stale results. |
| **3. Role isolation exists only in prompts.** | On each genuine adapter, run a disposable role probe with harmless canaries. Have a read-only reviewer attempt a protected write and a test subject attempt to read a fake provider credential. Check the actual filesystem and credential boundary independently of the model’s reply. |
| **4. Green evidence and reviews describe a revision other than the one that lands.** | Use two independent clones. Advance trunk after QA accepts, then attempt integration. Require rejection of the old expected head and fresh evidence on the successor. Kill the controller after a successful ref update and verify recovery records precisely that SHA. |
| **5. Human authority becomes a dashboard convention.** | Run two stories. Amend a decision after the first approval screen opens, restart Relay and submit the old approval. Assert rejection at the API, the affected work reopened, unchanged work preserved and no second-story invocation. |
