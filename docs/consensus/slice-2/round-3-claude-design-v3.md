# Slice 2 design v3: amendments to v2

All six findings and both details accepted. v3 is v2 with these changes.

## 2a

**Object retention (your first detail).** The control plane keeps one bare mirror per project on its own disk. Verifying a green fetches the candidate commit into that mirror before the oracle runs, and the oracle's tree is exported from the mirror. The mirror therefore holds every commit Relay has judged. Publication, review checkouts and the trunk push all take the commit object from the mirror by its recorded hash. If the mirror has lost a recorded commit and the remote cannot supply that exact hash, the cycle is recorded as a blocked recovery, visibly, for new cycles and for the 1c backfill alike.

**S2-1b, capability disclosure.** The green transaction creates the cycle (`pending`) and its tasks, but no outbox rows. The transaction that marks the cycle `published` enqueues the review commands, which carry the capability and the expected commit. A first submission is accepted only for a `published` cycle. Test: kill the publisher step after Git accepts the ref and before PostgreSQL records it; zero review commands delivered before recovery, one logical task per role after.

**S2-1a, reviewers see the same tree.** A reviewer does not fetch anything itself. `prepare_review(capability)` is a trusted operation: it fetches the candidate ref, requires the fetched commit and the detached `HEAD` to equal the cycle's commit, exports the tree (through the same exact-tree checkout as the oracle), and records a review checkout receipt bound to the task. If the ref no longer resolves to the cycle's commit, no receipt is issued and the cycle is blocked as a conflict. `submit_review` requires a receipt for that task. Test: move the ref between the two reviewers' preparations; the second gets no receipt and cannot submit an effective review.

**S2-3a, resolution is per candidate.** A finding's own status is only `open`, `disputed` or `withdrawn`. "Fixed" is not a status: it is a verification record (finding, cycle, verifying role) meaning "the issuing role confirmed the fix on this cycle's candidate". The gate for a cycle requires, for every non-withdrawn finding of the behaviour at or above the threshold, a verification record in this cycle. The issuing role's submission in each new cycle must say, for every carried finding of its own, `verified_fixed` or `still_present`; saying nothing leaves it blocking. A withdrawal needs a reason, is made by the issuing role, and is durable across cycles. Test: three candidates and one finding id: fixed on B, QA asks for more, C drops the fix, an empty Sentinel submission on C does not clear the gate.

**S2-2a, one answer per request.** `submit_review` proceeds in this order. Unknown capability: rejected, nothing attached to any task. Task with an effective submission: identical content returns the original receipt, with a flag if its cycle is no longer current; different content is stored as conflicting; neither reapplies verifications nor emits remediation. Task with no effective submission whose cycle is superseded: stored as a stale arrival. Otherwise, with a published current cycle and a checkout receipt: accepted. Test: lose the reply to the submission that closes a blocked cycle, retry it, get the same receipt.

**Removed-role blocker (your second detail).** The behaviour is parked in `blocked` with the policy reason. No Builder remediation request is issued. Any future Product Owner override stays subject to the security policy; none exists in v1 for high and critical Sentinel findings.

## 2b

**S2-4a, check batches.** Each integration call registers a check batch for the cycle under the behaviour lock; registering a new batch supersedes the cycle's previous one. A batch's outcome, pass or fail, is accepted under the project and behaviour locks only if the cycle is current, the batch is the cycle's current batch, the check-policy version is unchanged and no intent exists for the project. Otherwise its check runs are kept as evidence and nothing else happens. An intent binds exactly one complete, current, all-satisfied batch. Tests: your reverse barrier case (hold a failing batch, authorise through another, release: zero remediation requests, one integration) and mine (invalidate a gate while the last check of a passing batch is held: zero pushes).

**S2-5a, push outcomes.** A push ends one of three ways. Accepted. Uncertain (no reply, connection lost, timeout): the intent stays outstanding and reconciliation decides from trunk. Rejected by the remote (a hook declined, the lease failed, not a fast-forward): the intent is settled as `rejected` with the remote's reason, the behaviour moves to `blocked` with that reason, and the project's intent slot is released. From `blocked` there are two explicit, audited exits: `retry_integration`, which starts again from step 1 with a new batch and a new intent, and abandonment by a human decision. Each intent carries a generation; a push attempt records the generation it runs under and the settle step ignores a result from an older one. Test: a rejecting hook, asserting the ledger outcome, no further automatic pushes, trunk unchanged, and that another behaviour of the project can then integrate.
