### Stale bases

**Keep the strict stale-base rule for this slice.** An unrelated trunk change can still affect packaging, configuration or a regression. A new red cycle is a reasonable price for a simple guarantee. Read the remote outside the database lock, recheck the behaviour under lock, and enforce the expected head again at the push. The existing `reopen_red` accepts only `implementing`, so `review → validating_red` needs an explicit, audited transition that supersedes the candidate and reviews. [Current lifecycle guard](/Users/andrealaforgia/dev/relay-v3/src/relay/domain/behaviour.py:125)

Specify one exit from that path now. If the new trunk **already satisfies the contract**, another red cannot be obtained honestly. Record “already satisfied on new trunk” with its execution and send the behaviour for a product decision. Repeatedly asking the Verifier for a failing test would reward weakening the contract.

### Real Git and Docker

Push the **recorded local commit object** to the fully qualified trunk ref using its **explicit expected old SHA**. Fetching and verifying the candidate ref once, then resolving that name again as the push source, reintroduces the substitution race. Git’s force-with-lease compares the old ref value and can permit a non-fast-forward update, so Relay must separately establish ancestry for the exact base and candidate. Use a bare remote in acceptance tests. A normal non-bare fixture refuses pushes to its checked-out branch by default. Also test remote hook rejection and loss of the reply after the remote accepts the update. [Git lease semantics](https://git-scm.com/docs/git-push#Documentation/git-push.txt---force-with-leaseltrefnamegtltexpectgt) · [Git receive configuration](https://git-scm.com/docs/git-config#Documentation/git-config.txt-receivedenyCurrentBranch)

For Docker, keep the first required check within the existing oracle’s capabilities. It must run from a read-only checkout, in a pinned image, without network access. A project check that installs dependencies or writes build products into the checkout may be impossible in that profile. Record that as an unsupported check or an ineligible execution and block integration. Also decide what a required check trusts: a candidate-owned script printing “passed” cannot count as independent evidence of the behaviour under PO-1. Use a public-interface observation or a separately protected check definition. Then exercise a successful candidate with failures immediately before the push, after remote acceptance but before the reply, and after the database completion commit but before the caller receives success. Duplicate calls and restarts must converge on one integration record. Run the same fixture with a competing trunk advance and with a gate invalidated during checks.
